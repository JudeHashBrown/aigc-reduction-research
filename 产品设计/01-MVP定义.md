# MVP 定义

参考对象：[Pangram](https://www.pangram.com/)（纯检测，机构侧）、
[Phrasly](https://phrasly.ai/zh)（学生侧全家桶，中文本地化）

---

## 一、先看清这两个参考物是什么

| | Pangram | Phrasly | 我们 |
|---|---|---|---|
| 立场 | **抓人**（老师/高校/出版社/合规） | **帮人**（学生） | 帮人 |
| 核心 | 检测器 | 改写器 + 检测器 + **代写** | **诊断器** + 定向改写 |
| 输出 | 文档级分数 + 句级高亮 + AI辅助/全AI区分 | 分数 + 句级高亮 + 改进建议 | **逐句归因**（不报百分比） |
| 底气 | 99.7% 准确率，26 个模型基准，马里兰/芝加哥大学第三方验证 | freemium 全家桶 | 可核对的规则事实 |
| 分发 | 浏览器插件、Google Docs、Canvas/Moodle 等 LMS、API | 网页工作台 | 网页 |

**关键观察：Phrasly 的工作流是「生成 → 人工化 → 检测 → 再人工化」的迭代闭环。**
这印证了我们的验证闭环设计，但它把闭环做成了让用户手动循环；我们应该做成自动的。

**另一个关键观察：Phrasly 有 AI Writer 和 Thesis Generator。我们故意不做。**
代写是问题的来源，不是解法。做了它，产品定位立刻从"帮你把话说清楚"滑向"帮你造假"，
合规立场也守不住。

---

## 二、最重要的定位决策：**不要报「AI 率百分比」**

这是个信任陷阱，必须一开始就避开。

**为什么不能报：**

1. **用户只信学校用的那个检测器**（知网 / 维普 / 朱雀 / Turnitin）。
   我们自己算的百分比对他没有决策意义。
2. **Pangram 敢 claim 99.7% 是有底气的**——大规模标注语料 + 26 个模型基准 +
   第三方学术验证。我们第一天什么都没有。
3. **致命风险**：我们报"已降到 40%"，用户拿去知网测出 70% →
   **信任一次性归零，且他会告诉所有同学。**
   （现存五个方案里，AIGC-Detector-Pro 就在报"预估降至 XX%"，纯属自杀）

**改成报什么：可核对的事实。**

> 检出 **18 处** AI 特征，其中 **7 处**高风险
> · 第 3 段：三元并列 ×2、段末套句 ×1、AI 高频词 5 个（超阈值 2）
> · 第 7 段：模糊归因「研究表明」无出处、泛化结尾「具有重要意义」

**规则和统计的结论是可证伪的**——用户自己一眼就能验证"这段确实有 5 个高频词"
"加粗确实有 8 处"。**这种信任不需要预先验证过的分类器，第一天就能建立。**

内部可以有 0-100 风险分用于排序，但界面上要明确标注是**我们自己的启发式评分，
不是对任何检测器结果的预测**。

---

## 三、MVP 要验证的假设

> **可解释的逐句诊断 + 定向改写，效果和可信度都优于一键黑盒改写。**

整个竞品field（含 Phrasly、BypassAIGC）都是黑盒一键改。如果这个假设成立，
我们就有位置；不成立就得重想。MVP 的全部功能都应服务于验证它。

---

## 四、功能清单

### 必须有（缺一个假设就验证不了）

**1. 输入：粘贴文本**（≤5000 字）
- docx 上传不在 MVP，但紧随其后（BypassAIGC 的 `docx_io.py` 按段落号替换方案可直接复用，保格式）

**2. 诊断引擎**（纯代码，无 LLM）
- 规则层：AI 高频词表（分级加权）、句式模式正则（三元并列/否定排比/段末套句/模糊归因/泛化结尾）、格式检查（加粗数、破折号、要点列表）
- 统计层：句长均值与变异系数、段落长度分布、实词密度、**数字与专名密度**（具体性代理）、TTR、n-gram 自相似度
- 硬约束计数（来自 humanizer-zh-academic，全部可计算）：每段 AI 高频词 ≤2、全文段末套句 ≤1、每段三元并列 ≤1、全文加粗 ≤5、泛化结尾 0、模糊归因 0
- 段落打分：11 特征命中 +1，≥4 为高风险（确定性、可复现）

**3. 可视化：热力图 + 点击归因**
- 全文按句/段着色（红黄绿）
- 点任一句 → 弹出命中的具体规则、原文片段、为什么算 AI 特征
- 这是产品的**核心体验**，也是免费引流的钩子

**4. 两类修复分离**（我们的架构差异，要在 UI 上可见）

| | 确定性修复 | 语义改写 |
|---|---|---|
| 执行 | **代码**，毫秒级 | LLM |
| 范围 | 删填充词、替换词表内高频词、去多余加粗、破折号改写、拆长句合碎句 | 三元并列改递进、段末套句重写、无主句补主语 |
| 体验 | **即时预览每一处改动，可逐条接受/拒绝** | 需等待，整句替换 |
| 成本 | 0 | API 调用 |

> 竞品对所有改动都要等模型。我们让 70% 的修复即时完成且可审——这是可感知的体验差距。

**5. 交互式具体化（最小版）** ← 差异化的核心
- 对识别为"空泛"的句子，**不自动改写，而是提问**：
  > 「本方法有效提升了性能」——具体提升了多少？在什么条件下测的？
- 用户填真实信息 → 并入改写上下文
- **可跳过**（跳过则只做减法改写），保证低摩擦
- MVP 只对风险最高的 3-5 句提问，不要变成问卷

**6. 改写后重新打分 + 前后对照**
- 同一套诊断跑改写结果
- 并排 diff，标出每处改动对应的是哪条规则
- 未达标的句子可以再来一轮（限 2 轮）

**7. 噪声预算**
- 目标不是清到 0，是落进人类分布区间
- 每千字保留 2-3 处轻微特征，高权重特征（泛化结尾、段末套句）清零
- UI 上要说明为什么"没有全清"，否则用户会以为没改干净

### 明确不做

| 不做 | 原因 |
|---|---|
| 论文代写 / 大纲生成 | 问题的来源，不是解法；毁定位 |
| 降查重 | 策略与降 AI 冲突，另开通道 |
| 报 AI 率百分比 | 信任陷阱，见第二节 |
| 自训分类器 | 需要语料，Phase 2 |
| docx / PDF | 紧随其后，但不在 MVP |
| 复杂账号体系 | 卡密或邮箱链接即可 |

### 有余力再加
- **本地小模型困惑度**（Qwen2.5-0.5B，CPU 可跑）：逐句困惑度 + 方差，
  最接近第一类检测器的真实视角，五份资料无一实现

## 五、数据飞轮（低成本，但决定 Phase 2 的成败）

改写完成后引导用户：

> 「拿去你们学校用的检测器测一下，把改前改后的分数贴回来，帮我们校准。」

收到的是 `(改前分数, 改后分数, 检测器名称, 我们的特征向量)`。

这就是**免费的标注语料**。有了它才能：
- 验证阈值对不对（现在所有阈值都无出处）
- 知道哪些规则真的有用、哪些是噪声
- 训练自己的分类器（Phase 2）
- 反过来支撑"经 N 万次真实检测校准"这种**真实可claim的**说法

**这是 MVP 里最容易被忽略、但长期价值最高的一块。**

## 六、技术栈

- 后端 FastAPI；诊断引擎纯 Python（jieba/HanLP + numpy）
- 前端 React + Vite（热力图和逐句归因是重交互）
- LLM 走 OpenAI 兼容接口，模型可配
- PostgreSQL（要存诊断结果和校准数据）
- 工程外壳（任务队列、断点续跑、并发限流、卡密）参考 BypassAIGC

---

## 七、开发顺序与工作量（单人估算）

| 阶段 | 内容 | 天 |
|---|---|---|
| 1 | 诊断引擎：词表合并 + 规则 + 统计指标 + 打分 | 3-5 |
| 2 | 前端：粘贴、热力图、点击归因 | 4-6 |
| 3 | 确定性修复层（代码改写 + 逐条预览） | 2-3 |
| 4 | LLM 改写层 + 重新打分闭环 | 3-4 |
| 5 | 交互式具体化（最小版） | 2-3 |
| 6 | 校准回收表单 + 打磨 | 2-3 |
| | **合计** | **约 3 周** |

**第 1 阶段做完就能单独发布**——一个免费的"诊断报告"工具，
本身就有传播价值，而且能开始收集用户和校准数据。

## 八、MVP 成功的判断标准

不是"AI 率降了多少"（我们不报这个），而是：

1. **诊断准不准**：用户看到归因后，是否认同"这句确实有问题"（可用点击后的 👍/👎 收集）
2. **改写可不可用**：改完的文本用户愿不愿意直接用，还是要大改（收集"直接采纳率"）
3. **真实检测器的验证**：回收的改前改后分数，是否稳定下降
4. **留存**：用户会不会改完一章再来改下一章

第 3 条是硬指标，但要靠数据飞轮跑一段时间才有。前两条第一周就能看到。
